# 실전 수동 배포 운영 회고 및 체크리스트

## 문서 목적
- 이 문서는 실제 새 서버에 수동 배포를 진행하면서 드러난 운영 이슈와 해결 과정을 정리한 문서다.
- "구조는 맞는데 왜 실제 서버에서 안 뜨는가"에 대한 답을 남기는 것이 목적이다.
- 이후 Jenkins 자동 배포, HTTPS, Blue/Green으로 넘어가기 전에 반드시 다시 보는 문서로 사용한다.

- `372bb02` `build: ubot2.site 도메인 설정`

- `a991e94` `build: spring 빌드 이미지 변경`

즉 현재 수동 배포가 가능해진 핵심 축은 다음과 같다.
- 서비스별 Dockerfile 작성
- app/infra compose 분리
- `.env.local/.env.prod` 분리
- 백엔드 설정 구조화
- 새 도메인 반영
- Kafka 공식 이미지 전환
- ARM 서버 대응 Spring 빌드 이미지 수정
- KST 시간대 통일

## 이번에 새로 알게 된 핵심 운영 지식
### 1. 서버는 코드만 맞다고 바로 뜨지 않는다
실제로는 아래 네 가지가 모두 맞아야 했다.
- Git에 올라간 코드
- 서버에 직접 복사한 `.env.prod`
- Docker volume에 남아 있는 상태
- 서버 OS에서 이미 점유 중인 포트와 서비스

즉 "리포지토리 상태"와 "실제 서버 상태"를 따로 봐야 한다.

### 2. `.env.prod`는 Git에 없으므로 서버에 직접 복사해야 한다
현재 `.gitignore` 정책상 아래 파일은 Git에 없다.
- `backend/.env.prod`
- `frontend/.env.prod`
- `strategy_fastapi/.env.prod`
- `deploy/infra/.env.prod`

즉 `git pull`만으로는 배포가 완성되지 않는다.

### 3. external network는 서버에서 먼저 만들어야 한다
현재 app/infra compose는 모두 `ubot_app_net`을 external network로 쓴다.

즉 서버에서 먼저:
```bash
docker network create ubot_app_net
```
를 해줘야 한다.

### 4. 호스트에 직접 설치된 Nginx가 Docker Nginx와 충돌할 수 있다
실제 서버에서 infra 기동 시 `0.0.0.0:80 bind: address already in use`가 발생했다.

원인:
- 서버에 직접 설치된 호스트 Nginx가 80 포트를 이미 점유

확인 명령:
```bash
sudo ss -ltnp | grep :80
```

해결:
```bash
sudo systemctl stop nginx
sudo systemctl disable nginx
```

즉 앞으로는 "포트가 안 열림"뿐 아니라 "기존 프로세스가 먼저 열고 있음"도 먼저 의심해야 한다.

### 5. Kafka 이미지는 태그 호환성과 플랫폼 지원을 같이 봐야 한다
처음에는 `bitnami/kafka:4.0.0`를 사용했는데 실제 서버에서 manifest 오류가 났다.

해결:
- `apache/kafka:4.2.0`으로 전환

교훈:
- 새 서버를 세팅하는 단계라면 legacy 이미지보다 현재 유지되는 공식 이미지를 우선한다.
- 이미지 이름만 바꾸는 것이 아니라 환경변수 문법도 같이 맞춰야 한다.

### 6. Spring 빌드 이미지는 ARM 서버에서 태그 호환성이 다를 수 있다
처음에는 `gradle:8.13-jdk17-alpine` 기반이었지만 ARM 서버에서 manifest를 못 찾았다.

해결:
- builder 이미지를 `eclipse-temurin:17-jdk-noble`로 바꾸고
- 프로젝트의 `gradlew` wrapper를 직접 사용하는 방식으로 전환

교훈:
- 빌더 이미지는 "익숙한 태그"보다 "현재 서버 아키텍처와 wrapper 재현성"이 더 중요하다.

### 7. Nginx의 upstream 에러는 앱이 아직 안 뜬 중간 상태일 수 있다
infra만 먼저 올린 시점에는 `backend host not found`가 반복됐다.

원인:
- `default.conf`가 `backend`, `frontend`, `strategy_fastapi`를 upstream으로 참조하는데
- app stack이 아직 안 떠서 이름 해석이 안 됨

즉 infra만 뜬 상태의 Nginx 에러는 곧바로 설정 오류라고 단정하면 안 된다.

### 8. Kafka topic이 없으면 앱은 떠도 메시징 기능은 정상 동작하지 않는다
실제로 backend/strategy가 정상 기동한 뒤에도 `UNKNOWN_TOPIC_OR_PARTITION`이 떴다.

즉 Compose 성공과 기능 성공은 다르다.

최소 topic 생성 예시:
```bash
docker exec -it ubot-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic price.update --partitions 1 --replication-factor 1
docker exec -it ubot-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic signal.out --partitions 1 --replication-factor 1
```

### 9. Docker 시간대와 코드 시간대는 별개 문제다
처음에는 새 서버에서 `Redis 데이터 stale - 전체 리셋 필요`가 반복됐고 로컬에서는 재현되지 않았다.

원인 요약:
- 컨테이너는 UTC로 돌 수 있다.
- 코드가 `LocalDateTime.now()`를 KST처럼 가정하고 Upbit API 파라미터를 만들면 9시간 차이가 난다.

해결:
- app/infra compose에 `TZ=Asia/Seoul` 통일
- 백엔드 코드에서 중요한 `now()` 호출도 `ZoneId.of("Asia/Seoul")` 기준으로 명시

교훈:
- 컨테이너의 OS TZ와 애플리케이션의 시간 계산 로직은 둘 다 맞춰야 한다.

### 10. TZ를 고쳐도 기존 DB volume 상태는 남는다
KST 패치 후에도 60분봉/240분봉만 계속 stale가 났다.

실제 결론:
- 새 서버 MySQL volume 안에 이미 꼬인 차트 상태가 남아 있었고
- 코드 수정 후에도 그 상태를 재사용했기 때문에 증상이 이어졌다

최종 해결:
- MySQL volume을 초기화하고 다시 올림

교훈:
- 상태 저장소는 "설정이 고쳐졌으니 자동으로 정상화된다"라고 가정하면 안 된다.
- 특히 차트 sync, 메타 테이블, 캐시 재구성 같은 누적 상태는 volume 자체를 같이 의심해야 한다.

### 11. `docker inspect backend`가 된다고 해서 컨테이너라는 뜻은 아니다
운영 서버 추적 과정에서 `docker inspect backend`는 됐지만 `docker logs -f backend`는 실패했다.

가능한 이유:
- `backend`가 컨테이너가 아니라 이미지 이름일 수 있음

즉 컨테이너 추적은 먼저:
```bash
docker ps -a --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"
```
로 실제 이름을 확인한 뒤 해야 한다.

### 12. 현재 실행 중인 컨테이너가 어느 compose에서 떴는지는 label로 역추적할 수 있다
실제 운영 서버에서는 `app/docker-compose.yml`과 현재 돌아가는 컨테이너가 달랐다.

이때 유용한 명령:
```bash
docker inspect 컨테이너명 --format '{{json .Config.Labels}}'
```

특히 봐야 할 label:
- `com.docker.compose.project`
- `com.docker.compose.service`
- 가능하면 `com.docker.compose.project.config_files`

## 현재 수동 배포 절차
### 1. 최신 코드 반영
```bash
cd ~/Ubot_cicd
git pull
```

### 2. 서버 전용 env 파일 배치
직접 서버에 복사해야 하는 파일:
- `backend/.env.prod`
- `frontend/.env.prod`
- `strategy_fastapi/.env.prod`
- `deploy/infra/.env.prod`

### 3. 공통 네트워크 생성
```bash
docker network inspect ubot_app_net >/dev/null 2>&1 || docker network create ubot_app_net
```

### 4. 인프라 먼저 기동
```bash
docker compose -f deploy/infra/docker-compose.yml up -d
```

### 5. 앱 스택 기동
```bash
docker compose -f deploy/app/docker-compose.yml up -d --build
```

### 6. 기본 확인
```bash
docker ps
docker compose -f deploy/infra/docker-compose.yml logs --tail=100 nginx
docker compose -f deploy/app/docker-compose.yml logs --tail=100 backend
```

## 현재 프로젝트 기준 서버에서 자주 쓰는 확인 명령
### 컨테이너 목록
```bash
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"
```

### 네트워크 목록
```bash
docker network ls
```

### 공통 네트워크 상세
```bash
docker network inspect ubot_app_net
```

### app compose 서비스 로그
```bash
docker compose -f deploy/app/docker-compose.yml logs -f backend
docker compose -f deploy/app/docker-compose.yml logs -f frontend
docker compose -f deploy/app/docker-compose.yml logs -f strategy_fastapi
```

### infra compose 서비스 로그
```bash
docker compose -f deploy/infra/docker-compose.yml logs -f nginx
docker compose -f deploy/infra/docker-compose.yml logs -f mysql
docker compose -f deploy/infra/docker-compose.yml logs -f kafka
```

### compose 서비스명 확인
```bash
docker compose -f deploy/app/docker-compose.yml config --services
```

### compose 추적이 어려울 때 현재 실행 컨테이너 라벨 확인
```bash
docker ps -a --format "table {{.Names}}\t{{.Label \"com.docker.compose.project\"}}\t{{.Label \"com.docker.compose.service\"}}\t{{.Status}}"
```

## 이번에 실제 수정된 운영 기준
### 환경변수 전략
- `.env.local` / `.env.prod` 분리
- Git에 미포함
- 서버 직접 반영

### 도메인 전략
- 운영 도메인: `ubot2.site`, `www.ubot2.site`
- Nginx, CORS, prod redirect 설정 반영

### 시간대 전략
- 모든 서비스 기준 시간대: `Asia/Seoul`
- compose의 `TZ`와 코드의 `ZoneId`를 둘 다 맞춤

### 이미지 전략
- Kafka: `apache/kafka:4.2.0`
- Backend build: `gradlew` wrapper + temurin

## 한 줄 결론
이번 수동 배포에서 가장 중요했던 교훈은 이것이다.
- 서버 운영에서는 코드보다 상태가 더 큰 원인일 수 있다.
- `.env`, 포트 점유, volume, 컨테이너 시간대, 이미지 플랫폼 호환성까지 모두 봐야 한다.
- 수동 배포가 안정되면 그 위에 Jenkins와 Blue/Green을 올리는 것이 맞다.

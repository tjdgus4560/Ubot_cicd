# 최종 서버 배포 구조 가이드

## 문서 목적

- 구조 원칙, 디렉토리 배치, compose 분리 기준, 환경변수 전략을 한 곳에 정리한다.

## 왜 이런 구조를 택하는가
이 프로젝트는 학습자가 서버 한 대에서 프론트엔드, 백엔드, 전략 서버, 인프라 서비스를 모두 운영해보는 학습형 프로젝트다.

구조를 나누는 기준은 두 가지다.
- 관심사 분리: 자주 바뀌는 앱과 오래 유지되는 인프라를 분리한다.
- 생명주기 분리: 앱 재배포와 인프라 유지보수를 서로 다른 단위로 다룬다.

이 원칙이 현재 프로젝트에 적용되면 다음처럼 나뉜다.
- 앱 스택: `frontend`, `backend`, `strategy_fastapi`
- 인프라 스택: `nginx`, `mysql`, `redis`, `kafka`, `kafka-ui`, `jenkins`

## 최종 채택 구조
배포 관련 파일은 모두 `deploy/` 아래에 둔다.

최종 기준:
- `deploy/app/`
- `deploy/infra/`

`infra`라는 이름을 쓰는 이유:
- 이 묶음은 프록시만 포함하지 않는다.
- `mysql`, `redis`, `kafka`, `jenkins`처럼 상태 저장소와 운영 도구도 함께 포함한다.
- 따라서 `proxy`보다 `infra`가 실제 역할을 더 정확하게 설명한다.

## compose 묶음 단위
### `deploy/app/docker-compose.yml`
포함 서비스:
- `frontend`
- `backend`
- `strategy_fastapi`

이 묶음의 의미:
- 코드 변경이 자주 나는 실행 서비스
- 앱만 다시 빌드/배포하고 싶을 때 직접 다루는 묶음

현재 특징:
- 각 서비스는 `.env.prod`를 사용한다.
- 각 서비스는 `TZ=Asia/Seoul` 기준으로 동작한다.
- 외부 포트를 직접 열지 않고 `expose`만 사용한다.
- 외부 진입은 `nginx`를 통해 처리한다.

### `deploy/infra/docker-compose.yml`
포함 서비스:
- `nginx`
- `mysql`
- `redis`
- `kafka`
- `kafka-ui`
- `jenkins`

이 묶음의 의미:
- 외부 진입점
- 상태 저장소와 메시징 계층
- 운영 도구

현재 특징:
- `nginx`만 `80:80`으로 외부에 포트를 연다.
- `mysql`, `redis`, `kafka`, `jenkins`는 내부 네트워크에서만 접근한다.
- MySQL, Redis, Kafka, Jenkins는 named volume을 사용한다.
- Kafka는 `apache/kafka:4.2.0`을 사용한다.

## 네트워크 구성 원칙
두 compose가 분리되어 있기 때문에 공통 네트워크가 필요하다.

현재 기준:
- 공통 external network 이름: `ubot_app_net`

이 네트워크가 필요한 이유:
- `deploy/infra`의 `nginx`가 `deploy/app`의 `frontend`, `backend`, `strategy_fastapi`를 찾아야 한다.
- `deploy/app`의 `backend`, `strategy_fastapi`가 `deploy/infra`의 `mysql`, `redis`, `kafka`를 찾아야 한다.

즉 두 compose는 분리되어 있어도 같은 Docker 네트워크 위에서 만나야 한다.

## 환경변수 전략
현재 프로젝트는 서비스별, 환경별로 `.env`를 나눈다.

기준:
- 로컬 실행용: `.env.local`
- 서버 실행용: `.env.prod`

서비스별 파일:
- `backend/.env.local`
- `backend/.env.prod`
- `frontend/.env.local`
- `frontend/.env.prod`
- `strategy_fastapi/.env.local`
- `strategy_fastapi/.env.prod`
- `deploy/infra/.env.local`
- `deploy/infra/.env.prod`

핵심 원칙:
- Git에는 올리지 않는다.
- 서버에는 직접 복사한다.
- 앱은 각 서비스 폴더의 `.env.prod`를 읽는다.
- 인프라는 `deploy/infra/.env.prod`를 읽는다.

## 백엔드 설정 전략
### `.env -> application.yml -> Properties 클래스`
백엔드는 다음 구조를 사용한다.
- `.env.local`, `.env.prod`가 실제 값 저장소 역할
- `application.yml`, `application-dev.yml`, `application-prod.yml`가 Spring 설정 구조 역할
- Java 코드는 `@ConfigurationProperties`로 설정을 주입받는다

관련 클래스:
- `AppJwtProperties`
- `AppCryptoProperties`
- `AppOAuthProperties`

이 구조를 택한 이유:
- `@Value` 문자열 하드코딩보다 키 오타에 덜 취약하다.
- JWT, OAuth, 암호화 설정을 관심사별로 묶을 수 있다.
- 로컬/서버 환경이 바뀌어도 자바 코드 변경을 줄일 수 있다.

## 실행 흐름 예시
### 최초 1회
```bash
docker network create ubot_app_net || true
```

### 인프라 먼저
```bash
docker compose -f deploy/infra/docker-compose.yml up -d
```

### 앱 스택 다음
```bash
docker compose -f deploy/app/docker-compose.yml up -d --build
```

### 앱만 다시 배포할 때
```bash
docker compose -f deploy/app/docker-compose.yml up -d --build backend
```

또는 여러 앱을 같이:
```bash
docker compose -f deploy/app/docker-compose.yml up -d --build backend frontend strategy_fastapi
```

## Git에 올릴 것
- `deploy/app/docker-compose.yml`
- `deploy/infra/docker-compose.yml`
- `deploy/infra/nginx/conf.d/default.conf`
- `backend/Dockerfile`
- `frontend/Dockerfile`
- `strategy_fastapi/Dockerfile`
- Spring 설정 파일과 Properties 클래스

## Git에 올리지 않을 것
- 모든 서비스의 `.env.local`
- 모든 서비스의 `.env.prod`
- `deploy/infra/.env.local`
- `deploy/infra/.env.prod`
- 런타임 인증서/로그/데이터 디렉토리

현재 `.gitignore` 기준으로는 `**/.env`, `**/.env.*`를 기본 무시하고 `.env.example`만 예외로 둔다.

## 현재 구조에서 의도적으로 남겨둔 것
다음은 아직 최종 운영 단계가 아니므로 일부러 단순화했다.
- HTTPS 최종 설정
- Blue/Green 전환용 upstream 템플릿
- Jenkins 커스텀 Dockerfile
- bind mount 기반 데이터 디렉토리 표준화
- 모니터링/알림 체계

즉 지금 구조는 "수동 배포와 서버 운영을 이해하기 위한 실제 동작 가능한 최소 구조"에 가깝다.

## 최종 판단
이번 프로젝트에서는 아래처럼 정리하는 것이 가장 적절하다.
- 앱 스택과 인프라 스택을 분리한다.
- 위치는 프로젝트 루트의 `deploy/` 아래로 통일한다.
- 환경변수는 서비스별, 환경별 `.env.local/.env.prod`로 분리한다.
- 백엔드는 `@ConfigurationProperties` 중심으로 설정을 관리한다.
- 외부 진입은 `nginx` 하나로 통일하고 나머지 서비스는 내부망에 둔다.
- 런타임 산출물과 시크릿은 Git에서 제외한다.

즉 가장 핵심은 이것이다.
- 묶음 단위는 앱 스택 / 인프라 스택 2개
- 저장소 구조는 `deploy/` 아래로 통일
- 운영 자산은 Git과 서버 책임을 분리
- 시크릿과 런타임 상태는 서버 전용으로 관리

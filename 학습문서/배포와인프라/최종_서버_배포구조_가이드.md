# 최종 서버 배포 구조 가이드

## 문서 목적
- 이 문서는 현재 프로젝트에서 채택할 최종 배포 구조 기준 문서다.
- 이전에 나뉘어 있던 `단일서버_컴포즈_묶음전략.md`, `앱스택_프록시스택_분리구조_가이드.md`의 결론을 이 문서 하나로 통합한다.
- 앞으로 배포 구조 관련 판단은 이 문서를 우선 기준으로 본다.

## 왜 이런 구조를 택하는가
이 프로젝트는 학습자가 전체 배포 과정을 이해하기 위한 학습형 프로젝트다.

이론적으로 배포 구조를 나누는 이유는 다음 두 가지다.
- 관심사 분리: 역할이 다른 구성요소를 나누어 변경 영향 범위를 줄이기 위함
- 생명주기 분리: 자주 바뀌는 앱과 오래 유지되는 인프라를 구분하기 위함

이 이론이 현재 프로젝트에 연결되면 다음 구조로 이어진다.
- 앱 스택: `frontend`, `backend`, `strategy_fastapi`
- 인프라 스택: `nginx`, `mysql`, `redis`, `kafka`, `kafka-ui`, `jenkins`

즉 한 서버에서 운영하더라도, 무엇을 자주 교체하고 무엇을 오래 유지할지를 기준으로 나누는 방식이다.

## 최종 채택 구조
현재 프로젝트에서는 배포용 파일을 모두 `deploy/` 아래로 모은다.

최종 기준:
- `deploy/app/`
- `deploy/infra/`

여기서 `infra`라는 이름을 쓰는 이유:
- 이 묶음은 nginx만 포함하지 않는다.
- `mysql`, `redis`, `kafka`, `kafka-ui`, `jenkins`까지 포함한다.
- 따라서 `proxy`보다 `infra`가 실제 역할을 더 정확하게 설명한다.

## compose 묶음 단위
### `deploy/app/docker-compose.yml`
포함 서비스:
- `frontend`
- `backend`
- `strategy_fastapi`

이 묶음의 의미:
- 코드 변경이 자주 나는 실행 서비스
- 앱만 다시 배포하고 싶을 때 직접 다루는 묶음

### `deploy/infra/docker-compose.yml`
포함 서비스:
- `nginx`
- `mysql`
- `redis`
- `kafka`
- `kafka-ui`
- `jenkins`

이 묶음의 의미:
- 외부 진입점
- 상태 저장소와 메시징 계층
- 배포 도구

즉 이 구조는 동료가 사용했던 앱 스택/프록시 스택 분리 방식의 장점을 유지하면서, 위치만 `deploy/` 아래로 정리한 형태다.

## 지금 미리 만들지 않는 것
다음 경로들은 나중에 실제 운영 방식이 정해질 때 추가한다.

- `mysql/data/`
- `redis/data/`
- `kafka/data/`
- `jenkins/data/`
- `mysql/config/my.cnf`
- `jenkins/Dockerfile`

이유:
- bind mount를 쓸지 named volume을 쓸지 아직 확정되지 않았다.
- 실제 데이터 저장 경로를 지금 억지로 고정하면 오히려 구조가 불필요하게 커질 수 있다.
- Jenkins 전용 Dockerfile이 정말 필요한지도 아직 확정되지 않았다.

즉 지금은 반드시 필요한 배포 정의와 설정만 먼저 구조화한다.

## 네트워크 구성 원칙
두 compose가 분리되어 있으면 공통 네트워크가 필요하다.

추천:
- 공통 external network 하나를 만든다.
- 예: `ubot_app_net`

왜 필요한가:
- `deploy/infra`의 nginx가 `deploy/app`의 frontend, backend를 찾아야 한다.
- `deploy/app`의 backend, strategy_fastapi가 `deploy/infra`의 mysql, redis, kafka를 찾아야 한다.

즉 두 compose는 분리되어 있어도 같은 Docker 네트워크 위에서 만나야 한다.

## 실행 흐름 예시
### 최초 1회
```bash
docker network create ubot_app_net || true
```

그 다음:
```bash
docker compose -f deploy/infra/docker-compose.yml up -d
docker compose -f deploy/app/docker-compose.yml up -d --build
```

### 앱만 다시 배포할 때
```bash
docker compose -f deploy/app/docker-compose.yml up -d --build backend
```

또는 여러 앱을 같이:
```bash
docker compose -f deploy/app/docker-compose.yml up -d --build backend frontend strategy_fastapi
```

이 흐름은 "앱만 자주 교체하고 인프라는 오래 유지한다"는 구조적 의도와 맞닿아 있다.

## Git에 올릴 것
- `deploy/app/docker-compose.yml`
- `deploy/infra/docker-compose.yml`
- `deploy/infra/nginx/conf.d/*.conf`
- `deploy/infra/scripts/deploy_blue_green.sh`
- `backend/Dockerfile`
- `frontend/Dockerfile`
- `strategy_fastapi/Dockerfile`

## Git에 올리지 않을 것
- `backend/.env`
- `frontend/.env.local`
- `strategy_fastapi/.env`
- `deploy/infra/cert/**`
- `deploy/infra/certbot-logs/**`
- `deploy/infra/certbot-work/**`
- 이후 생길 수 있는 DB, Redis, Kafka, Jenkins 실제 데이터 디렉토리

## 최종 판단
이번 프로젝트에서는 아래처럼 정리하는 것이 가장 적절하다.
- 앱 스택과 인프라 스택을 분리한다.
- 위치는 프로젝트 루트의 `deploy/` 아래로 통일한다.
- 두 번째 스택 이름은 `proxy`보다 `infra`가 더 적절하다.
- 아직 확정되지 않은 data/config 전용 폴더는 지금 만들지 않는다.
- 인증서, 로그, env, 데이터 같은 런타임 산출물만 Git에서 제외한다.

즉 가장 핵심은 이것이다.
- 묶음 단위는 앱 스택 / 인프라 스택 2개
- 저장소 구조는 `deploy/` 아래로 통일
- 운영 자산은 Git 관리로 전환
- 런타임 산출물만 서버 전용으로 분리

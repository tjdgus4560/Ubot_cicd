### 현재 단계 해석
- 이 상태는 `학습문서/배포와인프라/배포학습_전체로드맵.md` 기준으로 보면
  - `2. 오라클 클라우드 인프라 기초`의 중반~후반부까지 진행된 상태다.
  - 아직 `서버 내부 기본 세팅`, `Docker 설치`, `배포 자산 재구성`, `첫 수동 배포`는 남아 있다.
- 즉, 지금은 "클라우드 진입 성공" 단계이지, 아직 "애플리케이션 배포 성공" 단계는 아니다.

### 현재 보안 규칙에서 보이는 점
- 현재 화면 기준으로 `22`, `80`, `443`, `8080` 포트가 열려 있다.
- `22`는 SSH 접속용으로 필요하다.
- `80`, `443`은 이후 Nginx와 HTTPS 운영을 위해 필요한 방향이다.
- `8080`은 Spring Boot 직접 점검용으로는 임시로 열어둘 수 있지만, 최종 운영 구조에서는 Nginx 뒤로 숨기고 외부 공개를 닫는 것이 맞다.

### 현재 상태에서의 판단
- 지금 당장은 `8080` 공개가 치명적인 잘못은 아니다.
- 다만 이 포트는 "첫 수동 배포 확인" 용도로만 잠깐 쓰고, Nginx가 앞단에 들어간 뒤에는 보안 규칙에서 제거하는 것을 목표로 잡아야 한다.

## 아직 남아 있는 것

### 1. 인스턴스 내부 기본 세팅
- OS 패키지 업데이트
- 타임존 확인

- 배포용 작업 디렉토리 구조 정리
- Docker, Docker Compose, Git 설치
- 필요 시 일반 사용자에 Docker 실행 권한 부여

### 2. 현재 프로젝트 기준 배포 자산 정리
- 현재 루트에는 `docker-compose.yml`이 없다.
- 과거 배포 자산은 `infra_isolated/` 안에 `Dockerfile`들과 `docker-compose.yml` 참고 흔적으로 분리되어 있다.
- 따라서 다음 단계에서는
  - `infra_isolated/`를 참고하되
  - 현재 코드 구조 기준으로 다시 수동 배포용 자산을 재구성해야 한다.

### 3. 운영 환경 변수 설계
- Spring Boot 운영 변수
- MySQL/Redis/Kafka 접속 정보
- OAuth2 및 JWT 관련 값
- Frontend의 운영 API URL
- 배포용 `.env` 또는 서버 환경 변수 주입 전략

### 4. 첫 수동 배포
- 목표는 Jenkins나 Blue/Green이 아니다.
- 가장 먼저 해야 할 목표는
  - Docker 기반으로
  - 서버에서
  - 직접
  - 애플리케이션을 띄우고
  - 헬스체크와 로그 확인까지 해보는 것이다.

## 지금 기준으로 가장 합리적인 다음 순서

### 1단계. 서버 내부 기본 상태부터 기록한다
- 왜 이 단계가 필요한가
  - 배포는 애플리케이션만의 문제가 아니라 런타임 환경과 리소스 상태 위에서 돌아간다.
  - 운영 환경을 모르면 장애가 나도 원인을 분리할 수 없다.
- 지금 해야 할 것
  - OS 종류 확인
  - 디스크 용량 확인
  - 메모리 확인
  - 타임존 확인
  - 열려 있는 프로세스와 기본 패키지 상태 확인

### 2단계. Docker 실행 기반을 만든다
- 왜 이 단계가 필요한가
  - 이 프로젝트의 수동 배포, 자동 배포, Blue/Green은 모두 결국 컨테이너 단위 운영 이해 위에 올라간다.
  - 즉 Docker는 단순 도구가 아니라 이후 배포 학습 전체를 지탱하는 실행 기반이다.
- 지금 해야 할 것
  - Docker 설치
  - Docker Compose 사용 가능 여부 확인
  - 테스트 컨테이너 한 번 실행
  - 재부팅 후 자동 시작 정책 확인

### 3단계. 현재 코드 기준 배포 자산을 다시 정리한다
- 왜 이 단계가 필요한가
  - 과거 배포 파일은 `infra_isolated/`에 격리되어 있고, 현재 기준 최신 정답이라고 가정하면 안 된다.
  - 따라서 지금 해야 하는 일은 "예전 파일 복붙"이 아니라 "현재 코드 구조에 맞는 새 수동 배포 자산 재구성"이다.
- 지금 해야 할 것
  - 현재 `backend` / `frontend` / `strategy_fastapi` 구조 확인
  - 각 서비스별 Dockerfile 사용 가능 여부 확인
  - 없거나 부족한 배포 파일은 현재 기준으로 새로 만든다
  - 최종적으로 `docker-compose.prod.yml` 또는 이에 준하는 수동 배포 파일을 준비한다

### 4단계. 첫 수동 배포 목표를 작게 잡는다
- 왜 이 단계가 필요한가
  - 처음부터 전체 스택 + HTTPS + Jenkins + Blue/Green까지 한 번에 붙이면 원인 분리가 거의 안 된다.
  - 작은 성공을 먼저 만들고 그 위에 단계를 쌓아야 학습도 되고 롤백도 쉽다.
- 지금 해야 할 것
  - 1차 목표: 백엔드 헬스체크가 서버에서 응답하는 상태 만들기
  - 2차 목표: 필요한 의존 서비스(MySQL, Redis, Kafka) 연결 확인
  - 3차 목표: 프론트엔드/전략 서버까지 포함한 수동 배포 성공

### 5단계. 그 다음에 Nginx와 HTTPS로 넘어간다
- 왜 이 단계가 필요한가
  - Reverse Proxy와 HTTPS는 "애플리케이션이 이미 정상 동작한다"는 전제가 있을 때 붙여야 원인을 분리할 수 있다.
  - 애플리케이션이 안 뜬 상태에서 Nginx까지 동시에 붙이면 어디가 문제인지 헷갈리기 쉽다.
- 지금 해야 할 것
  - 수동 배포 성공 이후
  - Nginx 구성
  - 도메인 연결
  - SSL 인증서 발급
  - `80 -> 443` 리다이렉트
  - 이후 `8080` 외부 공개 제거
